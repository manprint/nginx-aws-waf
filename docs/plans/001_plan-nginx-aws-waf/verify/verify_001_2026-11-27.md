## Findings
### V001-F1 — Publishing the CRL overwrites the live ingress CRL with a CRL from another CA
- Status: FIXED — 27-11-2026, V001-C1: TestCRL1_ PASS (FAIL without the fix), pki-isolation.sh ALL PASS, multinode.sh after pki.sh ALL PASS
- Severity: MAJOR. The ingress refuses every node; forwarding to central stops until a valid CRL is published again. The nodes buffer to disk, so no data is lost. This defect leaves the mTLS invariant of phase 5 without a guard, but it does not block dependent work.
- Category: divergent / regression (cross-test)
- Where:
  - `wafctl/cmd/wafctl/pki.go:publishCRL` (post-revoke/crl hook) and `wafctl/internal/central/ingress.go:PublishCRL`. These are units 5.2/5.3.
  - `tests/e2e/pki.sh` (5.1), which says it uses a "throwaway $WAF_PKI_DIR".
- Expected: the ingress uses only a CRL signed by the CA it trusts (`ingress/certs/ca.pem`), and an isolated test does not alter the lab.
- Actual:
  - `tests/e2e/pki.sh` isolates only `WAF_PKI_DIR`.
  - `pki revoke` → `publishCRL` writes the CRL of the "e2e" CA into `$WAF_DATA_DIR/central/ingress/certs/crl.pem` of the lab and reloads nginx.
  - Reproduced:
    - after pki.sh, the CRL md5 changes from c24c16…88 to cb72c6…e1 with issuer `CN = nginx-aws-waf CA e2e`;
    - `openssl verify -crl_check` on node2 → `unable to get certificate CRL`;
    - the ingress log shows `"CN=lab-node-2" FAILED:unable to get certificate CRL 500` (37 handshakes 04:28–04:30).
  - multinode.sh FAILED 4 (T-MN1, MN1-accepts, T-MN2, T-MN4) until `wafctl pki crl` restored the correct CRL; after that, ALL PASS.
- Impact:
  - In production, a `wafctl pki revoke|crl` with a different `WAF_PKI_DIR` on the central host has the same effect.
  - Running gates in the same session, G-U51 corrupts G-P5.
- Correction: C1
